# 标题检索 Steam AppID：准确率与效率调研（2026-10-24）

> 调研对象：网上成熟项目如何"根据游戏标题检索 Steam AppID"。
> 方法：GitHub 成熟项目源码级阅读 + Steam 端点现状实测（本文所有端点数据均为
> 2026-10-24 实测，非转述）。结论按"对本仓库匹配管线的可落地性"组织。

---

## 1. 结论速览

1. **Steam 官方全量清单 API（ISteamApps/GetAppList）已于 ~2025-11 弃用、现已彻底移除**（v1/v2 实测均 404）——"下载全量列表建离线索引"的经典方案失去了官方数据源，但社区每日镜像仍在运转（jsnli/steamappidlist，实测当天 autopublish），替代官方源 `IStoreService/GetAppList/v1` 需要用户自己的 Steam API Key。
2. **在线搜索端点搜不到已下架游戏**（实证：The Culling 435090 在 storesearch 与 SearchApps 均无结果，只返回无关的同名词游戏）——下载站上老游戏占比高，这是当前管线准确率的结构性盲区，只有离线全量目录能覆盖。
3. 成熟项目的匹配策略高度一致：**本地全量清单 + 归一化精确命中 → 分层宽松（前缀/去空格）→ 模糊相似度 + 明确阈值**（Dice 0.65 或 token_set_ratio 75 的经验值），绝不把模糊结果无条件当命中。
4. 对本仓库的可落地增量：在 nameIndex（学到的映射）与 storesearch（在线检索）之间**插入"全量目录离线索引"层**，并把社区英文搜索端点（SearchApps，免 key 极快）插为英文兜底层——详见 §4。

## 3. 成熟项目匹配策略对照

### 3.1 NikkelM/Steam-App-ID-Finder（CLI，批量名称→AppID）

- 数据：**本地缓存全量清单**（GetAppList，24h 缓存——该端点现已死，见 §2）
- 算法：先**精确命中**（大小写不敏感）→ 未命中走 `string-similarity.findBestMatch`
  （**Dice 系数**，对双字符组比较）取最高分 → **阈值 0.65**（作者经验值：
  "0.65 几乎找到全部正确匹配，更低开始出现误配"）
- 特性：`--only-full-matches` 严格模式；结果按相似度排序输出
- 启示：**本地清单 + 一次模糊计算**让批量查询零网络往返；阈值是防误配的核心

### 3.2 behaveproject/AppCategorizer（多源元数据聚合）

Steam 源（storesearch 第一个结果）经 `BaseSource.is_relevant()` **分层校验**
（阈值 `token_set_ratio ≥ 75`）：

1. 精确（大小写不敏感）→ 2. **归一化**（去全部空白）→ 3. 前缀规则
   （候选以查询开头 + `-`/`_` 分隔且 len≥5；查询以候选开头且 len≥5；候选以
   查询开头且 len≥4）→ 4. **rapidfuzz token_set_ratio ≥ 75**

- 启示：分层"由严到宽"逐级放行，模糊只兜最底层；归一化层解决空格/标点差异
  （对本仓库即 cleanPageTitle 之外的"候选名归一"维度）

### 3.3 本仓库现状（对照基线）

- 已有：nameIndex（学到的映射）→ 纠错库 → 动态缓存 → storesearch 逐词检索 +
  nameMatchesSearch 相关性校验 + matchCandidateScore 多候选打分 + 删词变体 +
  噪声自学习 → Bing → LLM → 三层缓存写入；英文交叉验证重搜（v14.3.1）
- 相对成熟项目的差距：①**没有全量目录层**——nameIndex 只含"用户命中过的"
  映射，未命中即走网络；②在线端点搜不到下架游戏（结构性盲区）；③相关性
  校验/打分是自有口径，未与社区经验值（Dice 0.65 / token_set 75）做过校准
  实验；④英文兜底层只有 Bing/LLM（重、慢），缺一个免 key 的轻量英文搜索层

## 4. 可落地建议（按收益/成本排序）

### 建议 1：新增"全量目录离线索引"层（准确率 + 效率双收益，核心建议）

在管线 nameIndex 之后、storesearch 之前插入 `appListIndex` 层：

```
nameIndex（学到的映射）→ 纠错库 → 动态缓存
  → ★ appListIndex（全量目录，离线）
      归一化精确命中 → 前缀/token 模糊（阈值校准）
  → storesearch（在线，中文主路径）
  → SearchApps（英文兜底，免 key）→ Bing → LLM
```

- 数据源**双保险**：主源 jsnli 每日 dump（`games_appid.json` ~20MB，raw 直取）；
  备源 `IStoreService/GetAppList/v1`（用户提供 key 时自建——`settings.steamApiKey`
  遗留键由此复活，"无消费方"豁免理由同步更新）
- 存储：走 STORAGE_MODULES 注册一行（OPFS 分文件，B5 写合并纪律）；
  内存索引按分层预热设计放温层（延迟加载，参考 steam-cache 模式）
- 匹配实现：归一化名 → appid 的 Map 先精确；未命中对**候选取回**（前缀/
  token 切片倒排或全量线性 + Dice——20 万条线性单次 ~10ms 级，SW 内可接受；
  如需更快可加 3-gram 倒排索引）
- **准确率增益**：下架/老游戏覆盖（storesearch 盲区，实证 §2）；**效率增益**：
  大列表批量场景免网络往返（现每 miss 一次 storesearch + 限速 150ms）
- 运维：jsnli 为个人仓库——dump 拉取失败/停更 7 天自动回退纯在线管线（熔断
  式降级，不阻塞主流程）；目录 7 天刷新一次即可

### 建议 2：阈值校准实验（准确率）

对本仓库 matchCandidateScore/nameMatchesSearch 用真实失败样本（纠错库 +
D&D 类 franchise 错配案例）跑社区阈值基线：Dice 0.65（App-ID-Finder）与
token_set 75（AppCategorizer）为起点，校准出本仓库口径的等价阈值；调研期间
未发现两者直接可比的公开基准——需以本项目样本实测。

### 建议 3：SearchApps 英文兜底层（效率，小改动）

`steamcommunity.com/actions/SearchApps/<term>`：免 key、毫秒级、返回
appid+name+icon——插在英文 storesearch 之后、Bing 之前，作为轻量英文兜底；
**仅英文可用**（中文返回空，实测），故只接入英文重搜阶段（v14.3.1 阶段 3）。

### 建议 4（参考，不急）：IGDB/SteamGridDB 映射

IGDB `external_games`（category 1 = Steam）可做"名称→元数据→AppID"的
替代映射，SteamGridDB 支持 `/steam/{appid}` 反查；对本仓库中文下载站场景
增益有限，列为未来可选数据源。

### 不建议

- 继续依赖 `ISteamApps/GetAppList`（已移除，任何教程/旧代码均失效）
- 引入 ML/embedding 做名称匹配（AppCategorizer 有 embedding 分类器，但其
  成本/复杂度对单条名称匹配不成比例；分层规则 + 阈值已是社区主流实践）
- 把模糊命中无条件当命中（两个成熟项目都用阈值硬卡——误配比未命中伤害大，
  与本仓库"未找到弹候选"的设计一致）
