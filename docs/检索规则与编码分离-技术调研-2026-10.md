# 技术调研：将"标题→AppID 检索"的工作规则与程序编码分离（2026-10）

> 问题：扩展里的检索工作规则——标题怎么清洗、检索词怎么生成、候选怎么校验、
> 打分怎么加权、什么算"相关"——目前全部硬编码在 `background/core/title-parser.js`
> 与 `background/steam/api-search.js`（合计 ~800 行）。能否像站点适配器规则包
> （adapters/，v3.0 已实现 JSON 声明式+规则市场）一样把它们分离为**数据**？
> 本文基于项目现状盘点 + 外部成熟项目调研（ludusavi / json-rules-engine /
> Steam-App-ID-Finder 等）给出选型结论与迁移路径。

---

## 1. 现状盘点：检索管线里有多少"规则"

| 规则类别 | 位置 | 现状形态 | 可分离度 |
|---|---|---|---|
| ① 标题清洗链（剥尾部噪声段/剥全角/剥括号注） | content/core/common.js cleanPageTitle + title-parser.js | 6-8 条正则硬编码 | ★★★ 高 |
| ② 下载站噪声词表（EN: build/crack/repack…；CN: 下载/汉化/破解…） | api-search.js NOISE_EN_WORDS + title-parser noisePatternAll | Set/正则字面量 | ★★★ 高 |
| ③ 版本后缀对照表（增强版↔Enhanced 等 8 对） | api-search.js VERSION_SUFFIX_PAIRS | 数组字面量 | ★★★ 高 |
| ④ 附属内容关键词（DLC/试玩/原声带…） | api-search.js ADDON/DEMO_NAME_PATTERN | 正则字面量 | ★★ 中（正则→数据需翻译） |
| ⑤ 候选校验流程（含词/序号对齐/跨语言信任/删词变体） | api-search.js nameMatchesSearch/Variant/matchCandidateScore | **代码逻辑**（控制流） | ★ 低 |
| ⑥ 打分权重（共同词+3/对齐+2/例外+1…） | api-search.js matchCandidateScore | 硬编码数字 | ★★ 中 |
| ⑦ 目录层归一化/保鲜/阈值 | app-list-index.js + PERF_CONFIG | 已单源常量 | 已完成 |

**关键判断**：⑤（校验流程的控制流）是管线的"骨架"，分离它=写规则引擎解释器，
复杂度与误配风险都高（v6.4.16/审查 A1 的教训：每条放行规则都是事故源）；
①②③④⑥ 是**数据形态的规则**，天然可声明式分离——这正是本项目站点适配器
已验证过的路线（v3.0 规则包 → v10.0 规则市场生态）。

## 2. 外部成熟项目调研

### 2.1 ludusavi（Rust，游戏存档备份，GitHub ~2.5k★）——同领域最贴近的先例

`scan/title.rs`：标题归一化是一条**正则管线**（7 条 RE_* 常量按序应用：年份尾缀
→ 版本词 → 商标符号 → 引号 → 空格压缩），正则清单内联在源码中，但**词表数据
（已知版本词、游戏别名）由社区维护的数据文件驱动**。

- 启示：**正则管线内联、词表外置**是同领域的务实折中——规则"骨架"稳定，
  易变的"词"走数据。本项目 ②③ 正是这个词表层。

### 2.2 json-rules-engine（JS 生态标准规则引擎，~1.5k★）

事实模型（facts）+ 条件树（conditions: and/or/not + operator）+ 事件。
支持 JSON 声明式规则、动态加载。

- 启示：适合"校验流程 ⑤"的部分外置——把 nameMatchesSearch 的分支判断
  改写为条件树。但代价：①管线每候选每词 2 次引擎求值（本仓库批量 60-130
  游戏 × 多词 × 多候选，性能敏感）；②条件树的表达力对"跨语言信任+数字
  对齐+序号例外"这类强语义规则很别扭（嵌套布尔+自定义 operator 仍是代码）；
  ③引入 300KB 级依赖，违背零构建零依赖铁律。**结论：不引入引擎库，自建
  微型 DSL（见 §3 选型）。**

### 2.3 Steam-App-ID-Finder / ludusavi 对照（§调研报告 §3）

两者的词表（版本词/噪声词）均为**代码内常量 + 少量配置项**——没有找到把
"标题→AppID 检索规则"完全数据驱动的成熟先例。原因：该管线的准确率来自
**规则的精确组合**（序号对齐/跨语言信任/删词校验相互咬合），声明式化后
每条规则的"为什么"注释与回归测试的咬合关系反而更难维护。

### 2.4 本项目自身先例（最有说服力）

站点适配器规则包（adapters/，v3.0）**就是一次成功的同类分离**：URL 特征/
选择器/列表结构全部 JSON 声明式，支持规则市场导入导出，并演进出了
features 布尔开关、校验白名单、逐站诊断（v10.0）。它成功的三个前提：
①规则是**纯数据**（正则/选择器/开关），无控制流；②消费端解释器（builder.js）
只有 ~300 行且稳定；③有规则包校验（validateAdapterRules）+ 规则市场生态。
检索管线规则若分离，需要满足同样三前提。

## 3. 选型结论：三层分离方案（自建微型 DSL，不引引擎库）

### 3.1 分层

**L1 词表数据层（本次推荐立即做）**——`rules/retrieval-vocab.json`：

```json
{
  "version": 1,
  "titleCleaning": {
    "stripTailSegments": ["下载", "游戏下载", "免费下载", "汉化版", "中文版", "绿色版", "免安装", "支持手柄", "解压即撸"],
    "stripTailSeparators": ["|", "-", "–", "—", "_"],
    "stripBracketed": true
  },
  "noiseWords": {
    "en": ["build", "plus", "full", "crack", "repack", "update"],
    "cn": ["下载", "游戏下载", "免费下载", "破解版", "汉化版", "中文版", "绿色版", "免安装"]
  },
  "versionSuffixes": [["增强版","Enhanced"], ["重制版","Remastered"], ["复刻版","Remake"], ["豪华版","Deluxe"], ["终极版","Ultimate"], ["年度版","Game of the Year"], ["典藏版","Collector"], ["黄金版","Gold"]],
  "addonKeywords": ["dlc", "demo", "试玩", "trial", "原声带", "ost", "artbook", "supporter pack", "支持者包", "内容包", "扩展包", "组合包"],
  "editionWords": ["edition", "enhanced", "deluxe", "upgrade", "remastered", "remaster", "definitive", "complete", "goty", "bundle", "collection", "demo", "trial"]
}
```

- 消费端：`background/core/retrieval-rules.js`（启动/首次消费时加载 + 缓存 +
  校验），title-parser/api-search/app-list-index 全部改读词表
- **收益**：新下载站噪声词/新版本对照/新附属关键词 = 改 JSON 一行（可随规则
  包市场分发！），不再改 4 个文件重发版；错题库新样本暴露的漏词可热修
- **校验**：validateRetrievalRules（类型/长度/去重/正则预编译——复用
  validateAdapterRules 模式）；**错题库回放测试即词表变更的验收门**

**L2 站特检索规则（中期，随站点适配器规则包 v3 演进）**——站点适配器已声明
URL/选择器；扩展 `features` 增加 `titleCleaningOverride`（个别站标题结构特殊
时站级覆盖清洗链，如 3DM 的"【汉化组】"前缀段）。挂入既有 adapter 规则
schema，不新建机制。

**L3 流程 DSL（不建议现在做）**——把 ⑤ 校验流程条件树化。理由：规则咬合
密（A1 审查：数字对齐/序号例外/跨语言信任相互依赖），DSL 化后每个反例的
归因成本更高；引擎解释器的性能/依赖代价（§2.2）；且"每条放行规则都有
回归测试+错题库"的既有防线已经覆盖了"变更不回退"的诉求。若未来词表层
维护量证明需要，再评估。

### 3.2 用什么技术与语言（直接回答）

- **不引入新语言/引擎**：MV3 SW 禁动态 import + 零依赖铁律 → 自建微型
  解释器（~150 行：JSON → 编译为正则/Set，启动时一次），语言仍是项目
  现用的原生 JS + JSDoc
- **数据格式**：JSON（与站点适配器规则包同构，可复用规则市场的导入导出
  UI/校验/分发链路）
- **分发**：词表内嵌默认值（代码内 JSON 常量）+ 可选规则包覆盖（走既有
  adapterRules 通道，version 字段升级）
- **回归防线**：错题库（tests/fixtures/mismatch-samples.json，已上线）+
  词表校验测试 + 930 用例——三层防线确保"变更不回退"

## 4. 迁移路径（建议拆 3 批，可穿插进第七轮）

| 批次 | 内容 | 规模 | 风险 |
|---|---|---|---|
| R1 | retrieval-vocab.json L1 词表层（②③⑥ 词表迁移）+ 消费端改造 + 错题库回归 | 中（~300 行） | 低（纯数据等价迁移，回放测试锁行为） |
| R2 | 规则包市场通道打通（词表可随 adapterRules 导入导出+校验） | 中 | 中（需规则 schema 版本升级） |
| R3（评估后） | ①清洗链声明式 / L2 站特覆盖 / L3 流程 DSL 评估 | 大 | 高（仅当 R1/R2 后维护量证明需要） |

## 5. 风险与反方观点（如实陈述）

1. **分离不等于变好**：站点适配器规则包的经验——声明式后单条规则的"为什么"
   注释与代码的强类型防线弱化，靠 validate + 错题库补。检索管线是全项目
   事故率最高的模块（v6.4.16/v6.4.19/v14.6.1 三次错配事故），迁移必须以
   错题库全绿为门禁，否则宁可不迁。
2. **性能**：词表加载后每次匹配走 Map/Set 查找（与现状同复杂度）✓；但
   正则预编译须在加载时一次完成（不能每候选现编译）。
3. **规则包供应链**：若词表可从规则市场导入，等于把检索准确率开放给第三方
   ——必须保留内置词表兜底 + 错题库门禁（建议 3.1 的 L1 先不做导入，R2 再开）。
4. **明确不做**：L3 流程 DSL、引入 json-rules-engine 等引擎库、i18n 化规则文案。
