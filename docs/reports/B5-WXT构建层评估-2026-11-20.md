# B5 构建层评估：WXT 迁移可行性（理论最优清单收束批）

> 2026-11-20 · 评估批次（不动代码）· 结论：**暂缓迁移，v15 构建器继续演进**

## 背景

「理论最优清单」（GitHub 热门项目导览筛选，忽略改造成本视角）将构建层理论最优
指向「上游维护的框架」——MV3 扩展生态首选 WXT（Vite 系，wxt.dev）。本报告评估
把 v15 自研 esbuild 双策略构建器（scripts/build.mjs）迁移到 WXT 的可行性。

## WXT 能力面（查证结论）

1. **非模块入口 IIFE 输出 ✓**：content scripts / unlisted scripts / MV2 background
   由 Vite bundle 为 classic（非 ESM）脚本——单入口单文件的 classic 输出是支持的
   （wxt.dev/guide/essentials/entrypoints.html）。
2. **HTML entrypoint 的多 classic script**：Vite 构建对 HTML 内 `<script>`（无
   type=module）不进依赖图、不 concat、不保序——**没有「多文件顺序 concat 保真」
   的原生语义**。本仓 7 个扩展页 × 50+ classic 页面脚本正是靠这个语义工作
   （跨文件裸标识符共享全局作用域）。
3. **实证同源教训**：v15 阶段 0 已实证 esbuild bundle 沿 ESM 边 tree-shaking
   会把 classic 全局作用域共享的模块整体摇掉（dash-stats ×5 模块丢失）——
   这正是自研构建器选择「页面 concat + content/background bundle」双策略的根因。
   WXT/Vite 是同一打包范式，该约束同样成立。

## 迁移的真实代价（不是换构建器，是换范式）

| 触点 | 现状（v15 单源） | WXT 迁移后 |
|---|---|---|
| 页面脚本 | concat 保真，零改动 | **50+ 文件 ESM 化重写**（裸全局 → import/export） |
| content 装载 | module-manifest 一行派生（tracker 装载/sim 文件表/integrity 校验三面单源） | entrypoint 化，派生面重建 |
| WAR | gen-war 单源派生 | WXT 自管 + 派生门禁重建 |
| shared 双形态 | classic 注入 + ESM import 双消费 | 必须统一形态（又一轮重写） |
| 门禁群 | perf-budget 四锁/gen-war/module-index/check:ast 全部指向现产物形态 | 全部重新锚定 |

量级评估 ≈ v15 绿地重构本体（阶段 0-5），且第一阶段 0 的教训会在 WXT 下原样重演。

## 收益对照

- **真实收益**：Chrome 破坏性变更的追维护外部化（框架上游承担）+ dev 模式 HMR
  + auto-imports。收益真实但**兑现前提 = 全量范式迁移**。
- **现役替代**：v15 构建器刚建成且全绿；Chrome 层面的破坏性变更（manifest v3
  演进）主要冲击 manifest 语义而非打包形态——本仓构建器对 manifest 生成没有
  重逻辑（手写 manifest + dist 镜像），上游框架在这一层的维护优势有限。

## 结论与建议

**暂缓迁移**。WXT 无法原生表达本仓的根基语义（classic concat + 全局作用域 +
三单源派生面），迁移 = 架构范式重写而非构建器替换，收益/风险比在当前阶段不成立。
「构建层理论最优」在本仓约束下的实际答案 = **自研构建器 + 上游变更观察**：
保留 WXT 作为观察项，若未来 Chrome 出 manifest/packaging 级破坏性变更、或页面
脚本完成 ESM 化（全量 TS 化的后续自然阶段）后再评估——届时迁移成本将大幅下降
（ESM 化完成后 WXT 的 entrypoint 模型直接可用）。

**与清单原始判断的差异登记**：评估前判断「上游维护框架赢过自研」；评估后修正为
「上游框架的收益以范式迁移为前提，本仓 classic 语义根基使该前提 = 全量重写」。
理论最优在约束世界里要重新计算——这是评估批次存在的意义。
