## 5. Findings（按严重性排序）

### 🟡 Warning 1 — [R1 认知过载 + R4 偶然复杂度] api-search.js 搜索管线混合三层职责

**Symptom:** [background/steam/api-search.js](../../background/steam/api-search.js) 共 690 行。核心函数 `searchSteamAppIdOnce`（L250–L505，约 255 行）同时承担：
- (a) **网络层**：2 次 fetchWithTimeout 重试 + `isCircuitOpen('store')` 熔断短路 + `recordSteamCall`/`recordDomainCall` 监控打点
- (b) **策略层**：多词循环（CJK 静态词 + 动态噪声词变体）内的候选打分、类型排名（game 优先于 DLC/音乐集）、相关性过滤、置信度早退（`CONFIDENT_SCORE=6`）
- (c) **终选层**：v14.8.2 新增的跨词共识收集（同一 appId 多词命中 → 每多一词 +2，封顶 +4）与共识 vs 高分的终选加成比较

外层 `searchSteamAppId` 另加：去数字重试（gamer520-123938 修复）+ 扩展组合搜索（generateSearchVariants + 动态噪声学习）+ 并行中英文搜索的失败兜底。

**Source:**
- Fowler — *Refactoring*, Long Method + Feature Envy（搜索管线内聚了网络 + 策略 + 终选三种职责）
- Evans — *DDD*, 领域逻辑（共识策略 / 相关性判断）散落在搜索管线内而非独立策略对象

**Consequence:**
- 改搜索策略（比如"加一条新的终选判据"）需要在 250 行长函数中定位三处叠加分支
- 错误回溯（gamer520-123938 一类案例）需同时追网络层 + 策略层 + 共识层，单次阅读成本 >10min
- 新成员读标题检索必须先爬 700 行才能理解"为什么这个词被跳过、那个 appId 被加成"

**Remedy:** 按"策略模式"拆为四个独立阶段，外层只做编排：
```
NetworkPhase   — 熔断 + fetchWithTimeout + 重试（API 监控打点保留）
ScoringStrategy — 名称相关度打分 + 类型排名（matchCandidateScore / rankCandidatesByType 已存在，聚合即可）
ConsensusStrategy — 跨词共识收集 + 终选加成（v14.8.2 独立子逻辑）
OuterOrchestrator — 去数字重试 + 扩展搜索（searchSteamAppId 瘦身到 ~150 行）
```
每个阶段独立 test 覆盖，错误回溯链路缩短到 ~150 行/阶段。对外签名 `searchSteamAppId(searchTerms, rawName, excludeAppId, lang)` **保持不变**，可独立发版。

**文件:** `background/steam/api-search.js` + 新增 3 个策略文件（或保持同文件内 `export` 分区，视团队偏好）
**影响面:** 搜索管线可测试性大幅提升
**风险:** 中（测试覆盖需补齐；Phase 签名保持稳定即无 API 破坏）
**优先级:** P2

### 🟡 Warning 2 — [R5 依赖方向] service-worker.js composition root 过重（34 imports）

**Symptom:** [background/service-worker.js](../../background/service-worker.js) 直接 import 34 个模块。其中 15 个是"温层预热目标"（`warmupRegistry` / `warmupWrongReports` / `warmupSiteAlertPersist` / `warmupLearnedNoise` / `warmupUrlIndex` / `warmupBehavior` / `warmupDownloadUrls` / `warmupOutboundAudit` / `ensureAppListIndex` / `loadSteamCacheToMemory` 温层补载等）。

膨胀来源：v14.5.0 B2 把原 `import()` 动态预热全部改为 **静态 import + setTimeout 延迟调用**（HTML 规范禁止 SW 顶层 `import()`，运行时 TypeError 被 allSettled/catch 吞掉导致原代码静默失效），import 数量从 18 膨胀到 34。

**Source:**
- Martin — *Clean Architecture*, Composition Root 应是"薄边界"（汇聚点不应承担业务逻辑）
- Ousterhout — *Philosophy of Software Design*, 深模块 + 简单边界，入口文件应只做组装

**Consequence:**
- 每次新增一个温层模块，SW 顶层需加一行 import + 一行 setTimeout body 调用——容易漏删废弃模块的残留 import
- SW 顶层代码体 ~320 行，其中 ~170 行是 import 声明 + ~60 行是温层 setTimeout body，真正的初始化逻辑（消息监听、alarm 注册、installed 处理、contextMenu）只剩 ~90 行
- 温层清单分散在 `import` 区和 setTimeout 体内两处——后续维护者需要同时对照两处才能知道"哪些模块属于温层"

**Remedy:** 抽取 `warmup-coordinator.js`：
- 温层 15 个模块的 import + `Promise.allSettled([...])` 放进该文件，导出 `runHotTier()` 和 `runWarmTier()`
- 热层（7 个目标）同理抽取
- SW 顶层 import 从 34 降到 ~15（核心初始化模块），顶层代码体中"import + setTimeout body"瘦掉 200 行
- 温层目标列表走导出数组，**后续新增温层模块只需改一个文件**

```javascript
// background/warmup-coordinator.js
import { /* 15 个温层模块 import */ } from './storage/...';

const WARM_TIER_TARGETS = [
  loadSteamCacheToMemory,  // 补载 detail/spy
  warmupRegistry,
  warmupWrongReports,
  // ... 其余 13 个
];

export async function runWarmTier() {
  await Promise.allSettled(WARM_TIER_TARGETS.map((fn) => fn()));
}
```

**文件:** 新增 `background/warmup-coordinator.js` + 修改 `background/service-worker.js`
**影响面:** SW 顶层瘦身，后续新增温层模块单点改
**风险:** 低（纯重构，行为不变；静态 import 图无新增文件——v14.5.0 修复已经把温层模块纳入 handlers 图）
**优先级:** P1（可立即做）

### 🟡 Warning 3 — [T6 测试架构 + T2 脆弱性] Visual gate ios17 主题偶发红

**Symptom:** 两次独立运行 `npm run visual` 均返回：
```
❌ ios17-options          差异 0.61%（阈值 0.5%）
❌ ios17-options-filters  差异 0.61%（阈值 0.5%）
```
其他 8 个主题（steam / cyberpunk / morandi）全绿。阈值定义在 `tests/visual-regression.mjs` L23：`const MAX_DIFF_RATIO = 0.005`。

**判定：** 0.11% 的超差量 + 两次一致 → **非 flaky，基线已失真**。ClearType 字体抗锯齿在不同 Chromium 版本 / Windows DPI / 字体渲染引擎更新后会稳定迁移。ios17 主题使用 system-ui 字体，抗锯齿差异比 steam（固定字体）大。

**Source:**
- Meszaros — *xUnit Test Patterns*, Erratic Test（"产生非确定性结果的测试"）
- Osherove — *Art of Unit Testing*, 测试隔离原则（环境依赖 = 脆弱测试）

**Consequence:** `npm run gate` 的 visual 步骤成为唯一偶发失败源，发布门禁信心受损。真正的 UI 回归被淹没在噪声里。

**Remedy:** 分两步：

**Step 1（立即）——刷新 ios17 基线：**
```bash
npm run visual -- --update
```
刷新后立即再跑 `npm run visual` 验证（期望全绿）。

**Step 2（长期）——单主题阈值放宽：**
在 `tests/visual-regression.mjs` 中将 ios17 主题阈值单独放宽到 `MAX_DIFF_RATIO_IOS17 = 0.01`（1.0%）。或截图前强制关闭字体抗锯齿：
```javascript
await page.evaluate(() => { document.body.style.fontFamily = 'system-ui'; document.body.style.fontWeight = 'normal'; });
await page.waitForTimeout(100); // 等字体稳定
```

**补充：** 把"字体抗锯齿波动 → 刷新基线"条目加入 CONTRIBUTING.md 或 scripts/gate.mjs 注释，避免下次再踩。

**文件:** `tests/visual-regression.mjs`（阈值调整）+ `tests/visual/baseline/ios17-*`（基线刷新）
**影响面:** visual gate 重新稳定
**风险:** 低（只改阈值/基线，不改业务）
**优先级:** P0（必须立即处理，否则 gate 不绿）

### 🟢 Suggestion 1 — [R1 认知过载] steam-cache.js 470 行持久化逻辑可拆分

**Symptom:** [background/storage/steam-cache.js](../../background/storage/steam-cache.js) 470 行混合：FIELD_MODULES 字段路由映射 + 内存 Map 读写 + dirtyModules Set 追踪 + 追加式 ratingLineCount 落盘 + legacy 旧单文件迁移 + 压缩重写触发。

**Source:** Fowler — *Refactoring*, Large Class + Middle Man（部分持久化逻辑委托）。

**Consequence:** 改缓存落盘策略（比如把 rating 模块的追加式改成 SQLite）需要同时理解 FIELD_MODULES 路由 + 追加行数追踪 + 重写判定三处。

**Remedy:** 抽取 `cache-persistence.js` 处理 dirty flush + 追加 + 压缩 + 迁移，`steam-cache.js` 只保留字段路由和内存 Map 操作。

**优先级:** P3（低优先级——注释质量足够，理解成本不算高）

### 🟢 Suggestion 2 — [R3 知识复制] searchSteamAppIdLight 与 searchSteamAppIdOnce 接口可统一

**Symptom:** `searchSteamAppIdLight`（api-search.js L560+）和 `searchSteamAppIdOnce`（L250+）结构几乎相同（fetch + 候选筛选 + 打分），但签名不同——light 版本多了 `bool allowCrossDomain` 和默认参数。

**Source:** Hunt & Thomas — *Pragmatic Programmer*, DRY。

**Consequence:** 改打分逻辑时需要两处同步。

**Remedy:** 提取 `searchOnce({ variants, strict, allowConsensus })` 单接口，light 版本传 `strict=false, allowConsensus=false`，Once 版本传 `strict=true, allowConsensus=true`。

**优先级:** P4（低——当前差异小，实际同步成本低）
