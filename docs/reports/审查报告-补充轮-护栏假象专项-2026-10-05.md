## 1. P0 级 — 门禁可被静默绕过

### 🔴 P0-1：覆盖率门禁的目录白名单，使 v14 本轮 8/11 个新增文件逃逸

`scripts/coverage-gate.mjs:16`：
```js
const COVERED_DIRS = ['background', 'content', 'adapters', 'data', 'shared'];
```

该白名单用于两处过滤（`:31` 与 `:40`）。**`dashboard/ options/ popup/ freegames/ hub/ welcome/` 的新增文件永远不进覆盖率门禁。**

而 v14 第四轮拆分的新增文件恰好主要落在这些目录（`git diff --diff-filter=A` 实测）：

| 提交 | 新增文件 | 是否在门禁内 |
|---|---|---|
| `210e0fd` B1 dashboard 拆分 | `dashboard/dash-backups.js` / `dash-diagnostics.js` / `dash-insights.js` / `dash-logs.js` / `dash-stats.js` | ❌ 5 个全逃逸 |
| `5146b99` B2 options 拆分 | `options/panels/favorites.js` / `search.js` / `sites.js` | ❌ 3 个全逃逸 |
| `4cb9188` B3 detail-page 拆分 | `content/detail/candidates.js` / `sidebar.js` / `tracking.js` | ✅ content/ 在门禁内 |

**11 个新增生产文件中 8 个（73%）逃过覆盖率门禁**，其中 dashboard 五模块合计 1182 行。

更严重的是 `vitest.config.js:79` 的 coverage `include` 同样只有这 5 个目录：
```js
include: ['background/**/*.js', 'content/**/*.js', 'shared/**/*.js', 'adapters/**/*.js', 'data/**/*.js'],
```
因此**全局 floor（`thresholds.lines ≥ 62`）的分母根本不含 UI 层代码**。实测被排除在外的生产代码：

| 目录 | 文件 | 行数 |
|---|---:|---:|
| options | 8 | 2420 |
| dashboard | 7 | 1270 |
| popup | 1 | 472 |
| freegames | 1 | 224 |
| hub | 1 | 75 |
| welcome | 1 | 31 |
| **合计** | **19** | **4492 行** |

即 **4492 行生产 UI 代码（占五目录生产代码 18778 行的 24%）完全在覆盖率统计之外**，门禁与全局阈值两道防线同时对它失效。

**影响**：「v14 把 dashboard 拆成 5 个新模块」这一重构的**质量完全没有被任何量化手段验证**，仅靠 E2E 冒烟的 DOM 存在性断言兜底（见 P1-2）。这是「重构做了、护栏没跟上」的典型盲区——覆盖率门禁给了"新增文件必须 ≥50% 行覆盖"的**承诺**，但目录白名单让这个承诺在最需要的地方成了空文。

**修复**：
1. `COVERED_DIRS` 补入 `dashboard` / `options` / `popup` / `freegames` / `hub` / `welcome`；
2. `vitest.config.js:79` 的 coverage `include` 同步补上（注意会拉低全局 floor，需下调 `thresholds` 或改分目录阈值）；
3. 过渡期可先对 UI 目录单独设较低阈值（如 ≥25%）建立棘轮，再逐步收紧，避免一次性爆炸。

### 🔴 P0-2：`scripts/lint-baseline.json` 是纯文档，零程序读取 —— 「棘轮」不棘轮

`scripts/lint-baseline.json:5-8` 声明：
```json
"tsNoImplicitAnyErrors": { "main": 891, "ui": 302, "content": 377 }
```
注释称「数字记录为棘轮参照：后续批次补类型后下调，**禁止上调**」。

**全仓搜索读取方（`grep -rn "lint-baseline" scripts .github package.json`）→ 零命中。**
没有脚本消费、没有 CI 步骤消费、没有 hook 消费。唯一提及处是 `迭代路线图-第四轮10批次-2026-09.md`（叙述性文档）。

**拆解**：

| 声明项 | 是否真的生效 | 说明 |
|---|---|---|
| `eslint: { errors: 0, warnings: 0 }` | ✅ 生效，但**不靠这个文件** | 靠 `package.json:13` 的 `--max-warnings 0`。本文件此段是冗余记录，**虚增了"棘轮已生效"的印象** |
| `tsNoImplicitAnyErrors: 891/302/377` | ❌ **完全是死数字** | 无任何程序测量、比较、上报。「禁止上调」靠人的自觉 |

**影响**：B9 批次声称建立了 lint 棘轮，实际只有 eslint 那半（且靠的是既有 `--max-warnings 0`）在生效，类型棘轮那半是纸面承诺。1570 处 noImplicitAny 技术债没有防劣化的机械保障。

**修复（约 30 行）**：
```js
// scripts/lint-ratchet.mjs
const base = JSON.parse(readFileSync('scripts/lint-baseline.json', 'utf8'));
for (const [cfg, key] of [['tsconfig.json','main'],['tsconfig.ui.json','ui'],['tsconfig.content.json','content']]) {
  let n = 0;
  try { execSync(`npx tsc --noEmit -p ${cfg}`, { encoding: 'utf8', stdio: ['ignore','pipe','pipe'] }); }
  catch (e) { n = (String(e.stdout).match(/implicit 'any'/g) || []).length; }
  if (n > base.tsNoImplicitAnyErrors[key]) {
    console.error(`❌ ${key} noImplicitAny ${n} > 基线 ${base.tsNoImplicitAnyErrors[key]}（禁止上调）`);
    process.exit(1);
  }
  console.log(`✅ ${key}: ${n} ≤ ${base.tsNoImplicitAnyErrors[key]}`);
}
```
然后加进 `scripts/gate.mjs` 与 `.github/workflows/ci.yml` 的 `test` job。

### 🔴 P0-3：`vitest.config.js` 的 include 显式清单，靠人记住 —— 漏加则静默不跑

`vitest.config.js:32-65` 用**34 项显式清单**枚举测试文件（本项目全部用 `.mjs` + `test-` 前缀，vitest 默认 glob 匹配不到）。

**正面核实**：清单 34 项与磁盘 34 个测试文件**双向零差异**（磁盘有清单无 = 0；清单有磁盘无 = 0）。当前无漂移。

**但机制风险**：`vitest.config.js:28` 与 `CONTRIBUTING.md:28` 都要求「新增测试文件必须加入 include 显式列表」——这是**纯靠人记住的约定，无任何自动化强制**。

实测验证：若新增一个 `.mjs` 测试文件而忘记加进 include，`npm test` **不报错、不警告、不执行**，门禁全绿而测试完全没跑。

**放大因素**：`fileParallelism: false` + `isolate: true` 让每个文件独立实例（设计正确），但也让「漏加文件」完全没有副作用暴露路径。

**修复（约 15 行，与项目既有 test-integrity 范式一致）**：
```js
// tests/meta/test-include-manifest.mjs（或并入 test-integrity.mjs）
const onDisk = globSync('tests/{unit,integration}/*.mjs');
const include = readFileSync('vitest.config.js', 'utf8');
const missing = onDisk.filter((f) => !include.includes(f));
test('所有测试文件均已登记进 vitest include 清单', () => {
  expect(missing, `漏加 include 的测试文件: ${missing.join(', ')}`).toEqual([]);
});
```
把「显式清单」从约定升级为**被强制的不变量**。

### 🔴 P0-4：`SITE_SCRIPT_FILES` 被 AGENTS.md 铁律 #13 列为单源，实为两份手工副本且零测试守护

`AGENTS.md:30` 明确宣称：「站点静态注入脚本另走 `background/core/site-scripts.js` 的 `SITE_SCRIPT_FILES`（manifest content_scripts）」，把它当作**已收敛的纪律**。实际：

- `background/core/site-scripts.js:33` — `const SITE_SCRIPT_FILES = [` ← **未 export**（模块私有）
- `manifest.json:71-84` — `"js": [ ...12 项... ]` ← **第二份手工副本**

`grep -rn "SITE_SCRIPT_FILES"` 全项目**仅 2 处命中**，都在该文件自身（`:33` 定义、`:77` 消费）。
`grep -rn "SITE_SCRIPT_FILES" tests/` → **0 命中**。

两份列表当前内容恰好一致（12 项逐项相同），故**当前无功能故障**。

**但这是本项目最危险的一类破窗**：
`test-integrity.mjs:241-259` 只断言 `adapters/` 子集三方一致，**未覆盖** `shared/patterns.js`、`shared/msg.js`、`shared/escape.js`、`content/tracker.js` 这 4 项。

**故障场景**：任何人新增一个共享脚本（如 `shared/crypto-utils.js`）到 `SITE_SCRIPT_FILES` 而忘记改 manifest →
- 用户**自定义规则站**（走 `syncSiteScripts()` 动态注册）→ 正常加载
- **内置站**（走 manifest 静态 content_scripts）→ 静默失败，不注入
- `npm run check` **全绿**

「一半站点正常、一半站点坏」的故障形态在生产环境极难定位——用户报"某些网站不生效"时，代码里所有测试都通过。

**修复**：
1. `const SITE_SCRIPT_FILES` → `export const SITE_SCRIPT_FILES`（1 个关键字）
2. `test-integrity.mjs` 新增断言：`JSON.parse(manifest).content_scripts[0].js` 与导入的 `SITE_SCRIPT_FILES` **深度相等**（顺序敏感）

一并修复关联问题 P2-1（`BUILTIN_DOMAINS` 测试用硬编码正则），见 §3。
