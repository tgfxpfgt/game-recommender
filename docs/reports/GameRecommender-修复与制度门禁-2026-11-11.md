## 0. 结论

1. 三项修复全部完成，各有回归测试与门禁；appListIndex 有**首次成功取用**的真实证据（20,247,815 B / 199,731 条 / Dota 2 → `570`）。

## 5. 分层与「改动 → 必须跑的最小门禁集合」

完整表见 `docs/specs/gr-hardening-2026-11-11/spec.md` 的 `## L3 分层与最小门禁集合（落地）`。摘录可提交条件：

**只跑 `gate:fast` 就可以提交**，当且仅当同时满足：

1. 改动**不**触及 `scripts/test-changed.mjs` 的单源白名单（常量/契约/存储注册表/词表等，触碰会自动升级定向验证）；

**必须 `npm run gate`（全量）**：发版触发点、改测试基建、改构建/打包脚本、跨层契约调整、性能/体积批次。

可信度：`gate:fast` 与全量共用同一套 vitest 配置与同一批门禁，差别只有"跑哪些测试"。`test-changed` 的映射表若失真，D-1 类假绿会回来——所以它的映射失败是红，不是跳过。

## 6. 运行期轨迹与回放

### 6.1 数据点（`background/storage/diag-trace.js`，`SCHEMA_VERSION = 1`）

| 字段                               | 回答什么                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------------- |
| `seq/t/stage/event`                | 哪个阶段、什么时候、发生 enter/exit/fail/stall/push/hit/miss/dump                       |
| `durMs`                            | 阶段耗时、单条耗时、停滞时长、冷启动耗时                                                |
| `failKind` + `httpStatus` + `host` | 失败类别（network/timeout/ratelimit/empty/notfound/parse）与是否 429/5xx，只留 hostname |
| `cacheLayer`                       | memory / session / opfs / negative / miss——命中哪一层                                   |
| `source` + `confidence`            | 主源/备源、匹配置信度                                                                   |
| `wave` + `counts`                  | 第几波、total/done/failed                                                               |
| `bytes` + `entries`                | dump 装载体量（首次运行证据）                                                           |
| `swWakeId`                         | SW 唤醒次数与归组                                                                       |
| `gameKey`                          | 游戏名 DJB2→base36 6 位哈希，会话内可关联、不可逆                                       |

**判据**：一份轨迹若能给出「最后一个有 enter 无 exit 的 stage」「该 stage 的 durMs 与最近 failKind」「波次 counts」「哪层缓存命中」，就能在不复现的前提下指出卡点。`classifyTrace()` 的返回即这四项 + `verdict` + `summary`。

### 6.2 隐私与体量

- 白名单键校验（`TRACE_KEYS`）+ 运行时剔除未知键；`assertAllowedKeys` 在测试里强制抛错。
- 不记录：完整 URL/路径/查询串、页面正文、游戏名、用户标识、appId 明文。
- 本地、环形 500 条、2 s 防抖落盘、随"清除数据"清空、不进默认备份、零出站。
- 体量：单条约 150–200 B，上限约 100 KB；典型会话 100–300 条 [推断]。性能：每事件一次对象分配、无同步 I/O，估算 < 1 ms/百事件 [推断，未做基准]。

## 8. 已知缺口（不掩饰）

1. **备源未真实取用**（G-2）：`first-run.json` 标为 `required:false` 并写明待回填，门禁不会因它假绿。
2. **首次运行证据是"登记制"**：`check:first-run` 能保证"没有记录就红"，不能保证"记录是真的"。真实性靠发布清单与轨迹文件复核。
3. **跨机器抖动**：墙钟预算 cap 取实测 ×1.5，重负载机仍可能假红；处理方式是隔离复跑，不是放宽 cap。
4. **战果数据不可考**：E-3 只能靠会话记录推断；若要根治，需要把每次门禁结果落盘成历史（下轮候选）。
5. **本轮未重测 F1 的 20–21 s**：软阈值常量与边沿语义有测试，端到端时序沿用 L1 批次结论。
6. **注释版本号漂移**（F-2）：新代码注释写 `v14.29.x`，实际版本 `14.28.9`；不影响运行，留待下批统一。
