# 游戏雷达三目标审查（2026-11-11）

> 审查维度：**用户体验（快、稳定）/ 资源占用 / 准确率**——按用户目标重排优先级，
> 不按代码质量维度。
> 纪律：先测后改。本文所有数字均标注「已实测 / 推断 / 不可测」；不可测项给可复现
> 的替代测量方法，不用推断值冒充基线。
> 边界：本次审查**未修改任何生产代码**，未 bump 版本，未执行 git 写操作。

## 0. 结论（先看这里）

**一句话**：前几轮修复里，「45s 强制收尾 + 未返回可点重查 + 缓存先行」是**真实生效**的；
但「20s 软看门狗」只让指标好看——它只写日志，**用户在 20–40s 之间看不到任何变化**。
用户说的"卡住"主要不是死锁，而是**反馈真空**，外加一个**语义错误**（网络故障被显示成"未找到"）。

| # | 结论 | 性质 |
|---|------|------|
| 1 | 热载（同 profile 二次加载）首个评分徽章 **289/297ms**，冷载 **15.6–18.2s**，约 **54×** 差距——缓存先行确实生效 | 已实测 |
| 2 | 网络不可达时：367ms 显示「0/4」→ **40.3s** 才出现「限流降速」→ 42.4s 起显示「未找到」。**20s 软阈值只落日志（`评分条目慢（不放弃）`），UI 无变化** | 已实测 |
| 3 | 根因已定位：进度只随「成波推送」下发（`ratings-batch.js` 的 `flushWave`），**停滞期零推送**——所以 stalled 文案即使算出来了也没送到页面 | 已实测（代码+运行双证） |
| 4 | 网络故障下 12 次 API 失败，后台正确地跳过了负缓存，但**前端仍显示"未找到"**——与"游戏不在 Steam"完全同形 | 已实测 |
| 5 | `appListIndex`（v14.6 上线的"全量目录离线层"）**自上线起从未生效**：URL 写死 `main` 分支，而仓库默认分支是 `master`（GitHub API 2026-11-11 确认），实测 404 | 已实测 |
| 6 | 准确率可量化程度低：错题库 28 条样本，**仅 4 条有 `expectedName`**；这 4 条里 2 条正确匹配被判「推测」（中文标题，sim=0.6） | 已实测 |
| 7 | 资源：SW 静态图 **890,346B / 106 文件**，超 780KB 预算 **91.6KB（+11.5%）**；OPFS 3 次加载共 **32 次写 / 35,437B**，其中 free-games 单次 22,953B 占 64.8% | 已实测 |
| 8 | SW 堆内存、常驻 CPU、真实 Steam 端到端时延：**不可测**（见 §5） | 不可测 |

**优先级判断**：先修「反馈真空」和「故障误标」（两者都是分钟级、小改动、直接对应
用户主观感受），再修 `appListIndex` 源与准确率样本——后者是准确率的**结构性前提**，
但修复本身会带来 20MB 级网络/磁盘代价，需要先定资源策略。

## 3. 目标 1 审查：用户到底卡在哪

### 3.1 三类"卡住"的判定

按用户要求拆成三类，逐一给结论：

| 类型 | 定义 | 本次判定 | 证据 |
|------|------|----------|------|
| **真实卡死** | 流程永久不推进，无终态 | **基本不存在** | 45s 强制收尾 + 120s 硬阈值 + 队列继续，实测 45.3s 全部出终态 |
| **等待过长但无反馈** | 有终态，但中间长时间 UI 静止 | **存在，且是主要体感来源** | 367ms → 40.3s 之间 UI 无任何变化（18–40s 真空）；热载 1/4 条目 ≥15s 停在「等待检索」 |
| **在跑但用户不知道** | 后台在推进，前端无体现 | **存在** | 后台 15s 心跳日志在推进（`评分任务心跳`），但该信号不下发页面 |

### 3.2 前轮修复是否真的让"卡住"消失（逐项验证）

| 前轮修复 | 代码位置 | 实测是否生效 | 用户可见效果 | 判定 |
|----------|----------|--------------|--------------|------|
| 45s 强制收尾 | `content/list/list-state.js:23`、`:365-375` | 是（45.3s 出终态） | 卡死有上限 | **有效** |
| 未返回 → 点击重查 | `content/list/list-state.js:235-245` | 是 | 用户可自救 | **有效** |
| 缓存先行 | `background/steam/orchestrator-list.js:81`、`:144` | 是（289/297ms） | 热载快 54× | **有效** |
| 20s 软看门狗 | `background/steam/ratings-batch.js:524-565` | 是，但**只写日志**（`:553`） | **无** | **只是指标好看** |
| 进度条 / `current/total` | `content/core/status-bar.js` | 有，但只在成波时更新 | 停滞时不动 | **部分有效** |
| 阶段文案（`卡在X步 Ns`） | `content/list/list-state.js:formatQueueStatusText` | 逻辑已就绪，**上游没送数据** | 实测未出现 | **未接通** |

### 3.3 根因（已定位，非推断）

`ratings-batch.js` 的进度与 stalled 信息**只挂载在成波推送**上：

- `flushWave()` 在「`pendingWave.size >= batchSize`」或收尾时才调用（`:585`、`:591`）；
- `progressPayload()`（含 `phase` 与 `stalled`）只作为 `STEAM_RATINGS_UPDATE` 的附带字段下发（`:459`）；
- 停滞时没有任何条目完成 → `pendingWave` 不满 → **一次推送都不发**。

所以 `stalledInfo()`（`:411-421`，20s 阈值）算得没错，`formatQueueStatusText` 也写得对，
但**数据没有离开 SW**。这解释了「后台日志 20s 有告警、UI 40s 才有反应」的整整 20s 差值。

### 3.4 次生问题：故障语义错误

网络黑洞场景下，后台日志是：

```
窗口内 12 次 API 失败（疑似网络问题），跳过负缓存
```

这个处理是**正确**的（不污染负缓存），但前端最终渲染「未找到」。用户得到的结论是
"这个游戏 Steam 没有"，而不是"网络不通"。这是准确性之外的另一类"用户被误导"。

## 4. 目标 2 审查：资源占用

### 4.1 体积

SW 静态图已超预算 11.5%。但要诚实说明：**当前没有可测的用户可见指标因此变差**——
冷启动模块图就绪 84–96ms，远低于感知阈值。因此本轮**不把"压体积"列为执行项**
（属于用户明确排除的"纯整洁类"），只保留红线：后续新增不要继续抬高。

### 4.2 OPFS 写入

稳态写量本身不大（3 次加载 35KB），但结构上有一处明显浪费：`free-games` 每次加载
**全量重写 22,953B**，占总量 64.8%，且内容大概率未变。这是"写放大"，不是"写量大"。

`appListIndex` 才是真正的资源大头，但它当前 404（见 §5.2），所以**现在是零成本零收益**。
一旦修好源，就会变成"每 7 天 20MB 下载 + 约 10MB OPFS"——这是一个必须先决策的权衡。

### 4.3 不可测项

- **SW 堆内存**：Chrome 未向 Service Worker 暴露 `performance.memory`；
  `performance.measureUserAgentSpecificMemory` 在 SW 中不存在；浏览器级 CDP 会话
  在本 harness 拿不到 target 域。**不可测**。
- **常驻 CPU**：同上，SW 内无计时器归因接口。**不可测**。

**替代测量方法（可复现，需人工）**：

1. Chrome 任务管理器（`Shift+Esc`）→ 找「扩展程序: 游戏雷达」→ 记录内存/CPU，
   在列表页停留 10 分钟（soak），观察内存是否单调增长（判断泄漏）。
2. `chrome://extensions` → 本扩展 → Service Worker「检查」→ Memory 面板 → 手动 GC 后取
   Retained Size，对比冷启动 / 批量检索后两个快照。
3. DevTools Performance 录制 SW 30s，看 Idle 占比与长任务（>50ms）数量。

依据：Chrome 官方《Service worker lifecycle》说明扩展 SW 在 30s 无事件后终止，且
`fetch()` 响应超过 30s 会终止事件——这正是本仓库把「批量内单次请求超时」压在 30s 内、
并用 15s 心跳保活的原因（[Chrome 文档](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)）。
OPFS 写入语义参考 [MDN：Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)。

## 5. 目标 3 审查：appid 匹配准确率

### 5.1 能说的和不能说的

- **能说**：28 条错题样本，硬失败 **0**——说明已知的错配模式都被护栏挡住了。
- **不能说**：不能把"硬失败 0"说成"错配率 0%"。分母是 28 条人工已知错题，不是随机抽样，
  既不代表线上分布，也没有"正确匹配被误判"的完整统计。
- **可量化的置信度分布**：只有 4/28 条能算（其余 24 条缺 `expectedName`）→ **不可量化**。

### 5.2 结构性发现：全量目录层从未工作

- `background/core/constants.js:183` 写死：

  ```
  https://raw.githubusercontent.com/jsnli/steamappidlist/main/data/games_appid.json
  ```

- GitHub API 实测（2026-11-11）：`default_branch = master`，`pushed_at = 2026-11-11T05:19:56Z`
  → `main` 不存在，必然 404。
- 后果：`app-list-index.js` 的刷新流程每次都走「拉取失败 → 6h 退避 → 回退纯在线管线」
  （退避常量见 `constants.js:110`，超时 `:108`）。调研报告建议 1 声称的"离线目录层"
  **名义存在、实际零覆盖**——`directory` 来源在置信度统计里出现 0 次就是证据。

> 这条同时修正了上一轮调研的一个默认假设（"建议 1 已落地"）。不是翻案建议本身，
> 是翻案"已落地"的判断。

### 5.3 置信度覆盖链路

| 链路 | 是否经 `attachMatch` | 置信度覆盖 | 性质 |
|------|---------------------|-----------|------|
| 列表批量首波（缓存 only） | 是（`orchestrator-list.js:144`） | 有 | 已实测（代码） |
| 列表批量第二波（在线） | 是（`orchestrator-list.js:418`、`:634`） | 有 | 已实测（代码） |
| 详情页缓存命中 | 是（`orchestrator-detail.js` `tryCacheServed` 分支） | 有 | 已实测（代码） |
| 详情页最终返回 | 是（`orchestrator-detail.js` 函数尾部） | 有 | 已实测（代码） |
| URL / 封面图直取 appId | 是（同上，`source='image'`） | 有 | 已实测（代码） |
| 用户纠正（`correction`） | 是，但**不强制 confirmed** | 有但语义不合理 | 已实测（代码） |
| 全量目录（`directory`） | 是 | **0 次触发**（源 404） | 已实测 |
| 免费游戏 / 系列 / 推荐 | 否（受信 appid，不做标题匹配） | 不适用 | 合理 |

### 5.4 已发现的假阳性

4 条可测样本中 2 条**正确匹配被判「推测」**：

- `gamer520-123938`：页面「生化危机4 重制版」→ Steam「Resident Evil 4」，`sim=0.6`，
  reason=`title-mismatch`；
- `gamer520-requiem-regression`：同类问题。

原因链：中文标题没有英文段 → 页面无数字 → 数字护栏返回 `0.6`
（`background/steam/match-confidence.js:172-174`）→ 取多段最大值仍 `< 0.75`
（`:25`）→ `suspected`（`:274`）。即：**中文站的正确匹配会系统性地被标成"推测"**。

## 6. 优化方案（按优先级）

> 每条标注动的是哪个**用户可见指标**、预期幅度、工作量、风险、以及「已实测/推断」。
> 纯代码整洁类不列入。

### P0-1 网络故障不要显示成「未找到」

| 项 | 内容 |
|----|------|
| 问题 | Steam 不可达时，列表条目最终显示「未找到」，与"游戏不在 Steam"同形，用户被误导 |
| 证据 | **已实测**：黑洞三域名后 42.4s 三项「未找到」；后台 meanwhile 日志「窗口内 12 次 API 失败（疑似网络问题），跳过负缓存」；`getSteamApiStatus().anomaly` 已在 `ratings-batch.js:378` 消费 |
| 改法 | 批量收尾/条目放弃时读 `getSteamApiStatus().anomaly`（或本批失败率超阈值），把该条目渲染为「⚠️ 网络异常·点击重查」，复用现有 `RETRY_GAME_LOOKUP` 点击重查；状态栏 summary 增加「网络异常 N 个」 |
| 预期指标 | 故障场景「误标未找到率」100%（3/3）→ 0；正常场景不变 |
| 工作量 | 小（约 30–60 行 + 1 个回归用例，就近 `tests/` 现有套件） |
| 风险 | 低。anomaly 有冷却窗口，文案用「网络异常」而非绝对断言；需保证不影响真实的「未找到」徽章样式 |

### P0-2 停滞期要有进度心跳（边沿触发）

| 项 | 内容 |
|----|------|
| 问题 | 进度只在成波推送时下发，停滞期 UI 完全静止 18–40s；20s 软阈值只写日志 |
| 证据 | **已实测**：367ms → 40.3s 无 UI 变化；代码 `ratings-batch.js:459`（推送唯一入口）、`:585/:591`（flush 条件）、`:553`（软阈值只 `Logger.warn`） |
| 改法 | 在 `stalledInfo()` 由 `null → 非 null` 的**上升沿**立即发一次轻量进度（不带 ratings，只带 `progressPayload()`），并加 5s 最小间隔节流；无需定时轮询 |
| 预期指标 | 停滞反馈首现 **40.3s → 20–21s（-50%）**；「0/4 不动」窗口从 ~18s 缩到 ≤5s |
| 工作量 | 小（边沿触发约 15–20 行） |
| 风险 | 低（推送频率有上限；`formatQueueStatusText` 已支持 `stalled` 渲染，不需改前端） |

### P0-3 修正 appListIndex 源，但先定资源策略

| 项 | 内容 |
|----|------|
| 问题 | 全量目录层 URL 指向不存在的 `main` 分支，自 v14.6 起从未生效 |
| 证据 | **已实测**：`constants.js:183` 为 `/main/`；GitHub API `default_branch=master`、`pushed_at=2026-11-11T05:19:56Z`；本轮 raw 域名在本机不可达（curl 000），**真实下载耗时不可测** |
| 改法（两步） | ① 先把 URL 改到 `master`，并把首刷从「搜索 miss 时无条件触发」改为「安装后空闲 + 后续 7 天一次」；② 观察 2 周再决定是否引入压缩（只存 `normName → appid`，约可再降 30–50%） |
| 预期指标 | 目录覆盖 0 → 理论上限约 20 万条（**推断**，本机无法验证真实收益）；代价：首次 20MB 下载 + 约 10MB OPFS，弱网下可能 45s 超时 |
| 工作量 | 改 URL 极小；空闲触发 + 资源护栏中等 |
| 风险 | **中高**。若用户网络不可达 raw/CDN，每次冷启动可能额外 45s 等待（现有 6h 退避是 session 级，SW 冷启动会重置）。建议这一步单独一版并观察，不与 P0-1/P0-2 混批 |

> 备注：这条是「准确率 ↔ 资源」的正面权衡，需要用户拍板；不建议直接裸改 URL 上线。

### P1-1 热载 1/4 条目未命中缓存（先定位）

| 项 | 内容 |

| 证据 | **已实测**：热载 3/4 条目 289/297ms，1/4 ≥15s；具体条目与 miss 原因未定位 |
| 改法 | 先给缓存 miss 加原因分桶日志（无条目 / 模块不完整 / 名字键不一致 / 平台预检拦截），拿到数据再改；不盲改缓存键 |
| 预期指标 | 热载命中率 75% → 100%（目标） |
| 工作量 | 定位 S；修复视根因 |
| 风险 | 低（只加日志） |

### P1-2 用户纠正来源强制 confirmed

| 项 | 内容 |
|----|------|
| 问题 | 用户人工确认过的 appid 仍可能显示「推测」，语义上不合理 |

| 工作量 | 极小（约 5 行 + 1 用例） |
| 风险 | 低（人工确认优先级本就高于自动相似度） |

### P1-4 中文标题的 0.6 数字护栏假阳性

| 项 | 内容 |
|----|------|
| 问题 | 中文标题 + 无数字 → 数字护栏直接给 0.6 → 正确匹配被判「推测」 |
| 证据 | **已实测**：`gamer520-123938`（生化危机4 重制版 / Resident Evil 4）、`gamer520-requiem-regression`，`sim=0.6`、reason=`title-mismatch`；`match-confidence.js:172-174` |
| 改法 | 不放宽 0.75 总阈值；只改数字护栏语义——「页面无数字」不应等同「低相似」，应交给其他段的最大值；仅在**双方都有数字且冲突**时降级 |
| 预期指标 | 中文站正确匹配的假「推测」率下降（幅度待 P1-3 的数据） |
| 工作量 | 小–中（改规则 + 用错题库回归验证不引入新误配） |
| 风险 | 中（放宽会提高"错配被标 confirmed"的概率，必须用 P1-3 的数据做前后对比） |

## 8. 建议的执行顺序

1. **P0-2（进度心跳）+ P0-1（故障文案）** —— 同一批做，都是列表页反馈链路，改动小、直接命中用户主观感受；
2. **P1-2（correction 强制 confirmed）** —— 5 行，顺手；
3. **P1-1（热载缓存 miss 定位）** —— 先加日志，拿数据再改；
4. **P1-3 → P1-4** —— 先让置信度可量化，再调规则，避免盲调；
5. **P0-3（appListIndex 源）** —— 单独一版，带资源护栏，需用户拍板；
6. **P2-1（free-games 去重）** —— 任意批次顺带。

> 所有生产行为改动在动手前应另起一批汇报结论；本轮只交付审查与方案。
