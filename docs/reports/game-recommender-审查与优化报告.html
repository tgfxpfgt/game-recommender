02

审查范围与方法

审查对象为附加文件夹 F:\data\browser extension\game-recommender 全部源码。四个审查视角并行展开：架构盘点（文件全集、引用链、模块划分、MV3 合规）、安全审计（注入面、消息传递、权限、存储、出站请求）、功能与数据流（缓存策略、API 降级链、通知与告警、口径一致性）、代码质量与 UX（重复、错误处理、i18n、可访问性、宿主样式隔离）。四路回传后由独立复核代理对 16 项关键声明做行号级抽核（第 11 节）。

  • 证据规范：每条发现必须给 file:line 与 ≤3 行源码摘录；行号经复核校准，偏差 ≤5 行。
  • 只读约束：审查全程未向目标目录写入任何文件。
  • 环境限制：本环境命令执行（exec）全局不可用 → 无法运行 lint/单测、无法加载扩展实测、无法截图；全部结论为静态审查。UI 现象类发现（P1-01、P1-04、P2-01）建议作者加载扩展后按验收路径确认。
  • 检索限制：Chrome Web Store 政策条文未能联网核实（检索无有效结果）→ 第 04 节的权限与远程代码结论来自直接代码核查，非政策条文比对。

架构评述

manifest 只声明 12 个内容脚本 + 1 个 service worker，但沿 import 链展开后实际约 147 个已验证文件，是一个四层架构的大型 MV3 扩展。分层统计（行数为约数）：

层文件数角色
shared/7经典脚本公共层：patterns / msg（统一消息+超时兜底）/ escape / settings-utils / crypto-utils / fm-keys / freegames-filter
adapters/8声明式站点规则（纯数据对象）+ builder 解释器；同一份规则被内容侧 DOM 解析与 SW 侧站内搜索双端消费
content/22装载器 tracker（经典脚本 + 运行时动态 import ESM，绕过 content_scripts 不支持 ESM 的限制）、core、list、detail、badges
background/56SW 入口 + handlers×14 + core×13 + storage×14 + steam×6 + recommend / sites / freegames
页面38popup 6 / options 14 / sidepanel 2 / dashboard 10 / freegames 3 / welcome 4 / hub 3
data/ + lib/4根级 OPFS 存储层（ND-JSON/JSON 分型）+ vendored jsQR（Apache-2.0，懒加载）
样式与主题20+content.css 516 行 + ui-theme + 19 个主题 CSS（逐一验证 2 个，其余按编号推断）

3.2架构亮点

  • 单源注册表纪律：五处历史上「散落多表手工同步」的痛点全部收敛为单源文件——content/module-manifest.js（内容模块清单）、data/storage-registry.js（存储模块）、background/core/message-contract.js（消息契约 + sender 门禁白名单）、shared/fm-keys.js、steam-rating-logic.js。
  • 演进式重构有履历：大量「壳 + re-export」（recommend/engine、freegames/manager、steam/api barrel、badges/core）保持消费方 import 路径不变；注释精确到修复批次号（B2/B5/B6/B7/B10），可溯源。
  • MV3 深坑有修复档案：SW 内动态 import() 被规范禁止导致 3 条链路静默失效的问题，v14.5.0 改「静态导入 + 延迟调用」修复（service-worker.js:18-29）；SW 冷启动消息竞态用 early-message-router（最早注册 onMessage）+ 内容侧排队冲放双向解决（tracker.js:126-160）；分层预热（热层启动即载 + 温层 15s，service-worker.js:186-210）；alarm 幂等创建防冷启动重置周期（service-worker.js:212-222）。

3.3架构弱项

  • 扩展页面（popup/options/sidepanel 等）用经典脚本按序共享全局，靠 /* global */ 注释约定（dashboard.js:1-2）——零构建的固有脆弱点，与内容侧 ESM 双轨并行增加心智负担。
  • data/ 与 lib/ 位于根级而非 background/ 下，「data 层不得 import background/*」仅靠注释约定（data-store.js:29），无机制强制。
  • 发现一处疑似死引用：settings-utils.js:52 goHub 的 page 取值含 'vista'（旧版菜单页），仓库中无对应文件（P3-04）。
04

安全与隐私审计

整体安全姿态好于同类社区扩展平均水平：核心攻击面（宿主页 → 扩展特权）被消息契约 fail-closed + sender 源门禁基本封死；出站请求统一加固。薄弱点集中在「新增字段未纳入既有清单」与「转义/协议校验职责层间推诿」两类系统性模式，共 2 项中危、无高危。

4.1中危 · 两项（建议随下版本修复）

P1-02中危 · 密钥泄露 + 虚假声明ITAD API Key 随导出/备份明文落盘，而设置页明文承诺会剔除
background/handlers/data-modules.js:57-73（剔除块 68-73） · background/storage/backups.js:53-59 · options/options.html:1131-1133

导出与备份链路只剔除 llmConfig.apiKey 与 steamApiKey，未处理 v6.4.19 引入的 itadProfiles[].key（与旧 itadApiKey）；而导入侧 rules.js:379-383 对 itadProfiles 强制置空并注释「ITAD 密钥配置不导入」——两侧不对称。更关键的是：设置页 ITAD Key 输入框下的提示文案明写「密钥仅存储于本机浏览器配置；导出/备份/导入自动剔除」，UI 承诺与代码行为直接矛盾，性质从潜在泄露升级为对用户的虚假安全声明。

修复：两处剔除逻辑补 itadProfiles（key 置空）与 itadApiKey，抽成单一 sanitize 函数供导出/备份共用；工作量约 30 分钟。回退方案（不推荐）：改 UI 文案如实披露。
P1-03中危 · 伪协议注入恶意规则包可借 searchUrl 注入 javascript: 链接
background/core/rules.js:66（searchUrl:'string'）+ 188-212（通用校验，无协议白名单） · content/detail/tracking.js:138 · shared/escape.js:20-26

规则校验对 searchUrl 只做「字符串 ≤500」通用校验，无协议白名单——对比同文件对 llmConfig.endpoint 强制 /^https?:\/\//i（rules.js:396）。后台把模板原样拼进响应的 searchUrl，内容侧浮窗以 href="${common.escapeAttr(site.searchUrl)}" 渲染「去搜索」链接；escapeAttr 只转义 & " < >，不拦伪协议。点击即在宿主页执行任意 JS。前置条件是用户导入恶意规则包（社交工程），但导入 UX 的「格式校验通过」会给人安全暗示。

修复：保存侧对 searchUrl 强制 http(s) 前缀（复用 endpoint 校验模式），渲染侧按 URL 解析再校验协议兜底；约 45 分钟。

功能与数据流

5.1存储：有界，不失控

「游戏缓存只增不减」不成立：steam-cache 按 meta / rating / detail / spy 四模块分文件（OPFS），各有 TTL + 双保险清理（全过期清除 + LRU 1200 条上限）+ rating 追加落盘带 compaction；其余存储均有 STORAGE_CAPS 单源上限。

模块TTL上限说明
steam-cache meta / rating / detail / spy30d / 7d / 72h / 7d（用户可调，0=永久）LRU 1200清理在 flush 时触发；TTL 全设 0 时仍有 LRU 兜底
app-stats（跨站累计）永不过期20000徽章文案自述；建议提供清理入口（P3-06）
url-index（URL→appId）—5000负缓存 2h；熔断期有网络守卫，不固化「未找到」

5.2降级链与口径

  • 六级定位降级：错误纠正库 → URL/名称索引 → 全量目录（免网络）→ storesearch → 英文段/社区搜索 → 详情页信号回捞（预算 8）；某级失败自动降级，Metacritic 仅主机游戏且限额。
  • reviews 端点 302 死亡回退：回退商店页 HTML 三形态解析（api-reviews.js:~271-300），强制 l=schinese，desc 由阈值映射反推——回退路径的分档文案可能与官方九档在边界有出入（P3-07 一并文档标注）。
  • 好评率口径：全时段好评率 = 官方 query_summary 的 positive/total 自算（全语言），与 Steam 商店页一致 ✓；30 天好评率基于「最新 100 条评测」自算（api-reviews.js:151, 118-137），30 天内评测 >100 条的热门游戏（如新 3A 首月）会偏离 Steam 真 30 天聚合，首月通常偏悲观——建议 UI tooltip 标注口径（P3-07）。
  • 负缓存网络守卫：Steam 熔断期间不把「网络失败」固化为「未找到」（orchestrator-list.js:284-300），恢复后自动重查 ✓。

5.3通知与 alarms：两处 P1 级小 bug

  • P1-05 资源泄漏：批量好评率任务变陈旧（>1h，ratings-batch.js:117, 269-272）时 stale 分支只清除任务、不拆除 1 分钟周期的 resume alarm → SW 被无限每分钟唤醒（电耗/性能），直到下次成功任务收尾。修复 ≤10 行。
  • P1-06 通知重复：收藏折扣提醒无防重标记（itad.js:134-144），而同函数内发售提醒有 grReleaseNotified:+appId 标记（:158）；favPriceCache TTL 24h < 折扣轮询周期 48h，缓存必过期 → 同一持续折扣每 48h 重推。修复：仿发售提醒加标记。
  • 限免链路本身健康：逐源 try/catch 静默降级（单源挂了只少一个源）、固定通知 id 聚合 + 仅推 fresh 新增 + 新增去重，不骚扰 ✓。
